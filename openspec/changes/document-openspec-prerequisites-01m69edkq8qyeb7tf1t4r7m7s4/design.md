# Documentation structure and installation boundaries

## Context

See [proposal.md](proposal.md) for motivation and scope. A short design is warranted because similarly named installation mechanisms cross different trust, profile and execution boundaries.

Observed source at the proposal base:

- `README.md` documents the five companion packages, a four-package Hermes loop and GUI-first companion installation. Its OpenSpec prerequisite statement does not explain upstream acquisition.
- `docs/claude-installation.md` already distinguishes account plugins, individual uploads, Code-tab execution and optional orchestration. Preserve those boundaries and its primary-source citations.
- `docs/openspec-workflow.md` pins OpenSpec 1.15.0, lists six core actions and the expanded verification workflow, and makes verification advisory.
- `scripts/install-local-skills.mjs` discovers this repository's canonical packages only. Neither it nor `.claude-plugin/marketplace.json` installs upstream OpenSpec. Documentation must not imply otherwise.
- `tests/documentation.test.mjs` checks GUI-first guidance, the original four-package companion loop, counts and authority language. `tests/native-installation.test.mjs` executes the existing native companion helper in scratch homes. Preserve those recipes and headings rather than repurposing them for upstream skills.
- `local-skill-installation` is the only current capability spec and governs installer behavior, not this documentation addition. The new change opts out of specs using native `skip_specs: true`.

## Goals / Non-Goals

Goals: provide a single navigable prerequisite guide; preserve reproducibility, explicit selection and host-specific verification; keep instructions synchronized with future skill/dependency changes in the same change; describe installation without implying authorization to execute a change.

Non-goals: automated setup, a new distribution bundle, release/version upgrades, actual user/profile/account installation, changes to tests or packaged bytes, and claiming equal tools or workflow execution across hosts.

## Decisions

### 1. One canonical upstream guide, short links from existing entry points

Create `docs/openspec-installation.md` with: prerequisite layers; explicit seven-skill table; CLI/version check; Hermes; Claude Desktop/Code; Codex; verification/updates; primary references. Add concise links near the existing prerequisite/install entry points in the three existing documents. Keep companion commands intact, especially the first `for skill in ...` loop relied on by existing tests.

Alternative: duplicate all host recipes in the README and Claude guide. Rejected because skill selections, security caveats and version instructions would drift.

### 2. Release-aligned upstream content, not another package owner

Retain CLI 1.15.0. Prefer a reviewed upstream release/tag or skills generated by the matching CLI when supplying reproducible recipes. A direct source-qualified Hermes install and the native skills CLI's explicit selection are available mechanisms; verify the precise release-target syntax in isolation before publishing a recipe. If showing `skills-sh/fission-ai/openspec/<name>` or `npx skills add fission-ai/openspec`, explicitly explain that these resolve upstream content rather than guaranteeing the project's CLI pin. Do not claim that current skills are incompatible merely because upstream main has advanced; compatibility requires evidence.

The upstream v1.15.0 repository contains the propose package, and its CLI exposes `context` and `store`. Those command names alone are not evidence of a version mismatch. Account ZIPs must preserve complete reviewed upstream packages. Document manual preparation only; this repository will not generate or host them.

Alternative: vendor upstream skills or add an `openspec-core` plugin. Rejected for this change because the operator selected documentation only and the existing distribution contract excludes upstream actions.

### 3. Make host destinations and skill state explicit

- Hermes: use the selected `-p <profile>` throughout inspect/install/list/configuration steps. Explain skills.sh community trust and normal scanner-managed installation; stop on findings. Show how to identify already-installed disabled skills and enable only the seven names, without reinstalling or changing unrelated exclusions. Do not hardcode the default profile as the destination.
- Claude Code, including Desktop's Code tab: use user-global skills with explicit upstream selection, review/collision handling and `/openspec-propose` invocation. Explain `/opsx:*` command-file spelling only when those files were actually installed; a skill-directory copy is not command generation.
- Codex: use user-global `~/.agents/skills`, explicit selection, `/skills` or `$openspec-propose`, and note the shared directory is not Codex-exclusive. Do not invent a `codex skills install` subcommand.
- Claude Desktop account UI: distinguish complete individual skill ZIP uploads from this repository's companion plugin/ZIPs and from local CLI installation. Explain package preparation, enablement and organization policy. No verified upstream marketplace or ready-made upstream ZIP is assumed. Ordinary Chat is not a capable local Git/OpenSpec execution host merely because a skill uploads. Cowork needs its own actual tools/workspace access.

Alternative: one generic install-all command for every host. Rejected because it includes upstream-maintainer release/docs workflows, targets different scopes and cannot establish Desktop execution compatibility.

### 4. Separate installation, discovery, compatibility and authority

A successful download or ZIP check proves neither skill loading nor end-to-end execution. Use each client's real inventory/picker and loaded path where available. Show a read-only inspection request; do not use proposal/apply/archive as an installation smoke test on real project records. Preserve local customizations before updates and avoid duplicate account/plugin/directory copies. Distinguish Hermes hub updates, native skills CLI updates, generated adapters and uploaded snapshots; none is this repository's local companion update mechanism.

The seven packages are the selected setup inventory, not permission to bypass `openspec-delivery`: orchestrator-only Git/tasks writes, one approved task group, independent review and finish authority remain unchanged. `openspec-verify-change` stays advisory, not a CLI `openspec verify` gate.

### 5. Treat prerequisite changes and instruction updates as one deliverable

Add a durable rule to root `AGENTS.md`, with an operational maintenance section in `docs/openspec-installation.md` and a matching requirement/link in `docs/openspec-workflow.md`. A change that adds, removes or renames required OpenSpec skills, alters their prerequisite relationships, changes CLI/runtime versions or companion dependencies, or changes a supported installation route must assess documentation impact and update every affected current instruction in that same change. This change establishes the rule; it does not alter those prerequisites itself.

The impact check covers the canonical skill inventory, required/optional distinctions, version/source pins, CLI/runtime/host prerequisites, per-host installation and enablement commands, update/removal instructions, verification steps, counts and cross-links in the README and installation/workflow guides. Update affected surfaces rather than mechanically editing unrelated text. After a prerequisite removal or replacement, explain any operator-reviewed migration and preserve existing collision, backup and scanner boundaries; catalog absence is not automatic uninstall authority. Existing archived plans/evidence remain historical records, not installation instructions to rewrite.

The author owns the synchronized documentation delta and the reviewer compares it with the resulting skill/dependency configuration and available gate/probe evidence. Missing or contradictory affected instructions block completion before integration/publication. Record verification truthfully; the policy does not create an automated enforcement mechanism, permit scanner bypasses or imply real client installation. Required commands and documentation checks must be rerun after the update, with existing relevant tests adjusted by the future change when necessary and authorized.

Alternative: update instructions in a later documentation-only follow-up. Rejected because it leaves a supported setup path stale between prerequisite changes and their instructions. Merely adding a reminder to the new guide is also insufficient: the root contributor contract must make the obligation discoverable to future skill/dependency work.

## Verification approach

Implementation is limited to the five documentation/contract files named in the proposal. Use an ad-hoc content/link audit plus existing tests rather than changing production/test code for this docs-only request. Check the exact seven names, cited sources, destination/invocation spelling, CLI/skill/companion distinction, scanner/collision caveats and explicit GUI limitations. Confirm the root contract and installation/SDLC guidance state both maintenance triggers and the same-change completion condition; audit affected host recipes and inventories against the documented prerequisites, rather than claiming existing tests automatically enforce this new policy.

Exercise documented command syntax/package preparation in scratch homes/workspaces beneath the configured scratch root. Disable optional telemetry during discovery probes, avoid credentials, and never redirect a test back into real profiles or client homes. Hermes scan rejection remains a failure/blocker, not a reason to switch installers or force installation. Where a client/GUI is unavailable, report source verification and package checks separately from unperformed client loading/acceptance.

Run existing focused documentation/native-installation tests, `npm test`, `npm run build`, local metadata validation, native strict validation and `git diff --check` after the final edit. Check that generated inventory is still five companion packages/two plugins and no canonical packages or manifests changed. Keep evidence temporary or in the selected change under existing policy, not a new progress tracker.

## Risks / Trade-offs

- Moving upstream documentation or installer flags drift -> cite primary sources, record exact versions used by isolated probes, and retain the CLI pin.
- Later skill/dependency changes leave setup instructions stale -> require an explicit documentation-impact check, synchronized edits and renewed verification within the same change; reviewer blocks completion on stale affected guidance.
- Account upload rejects upstream metadata or host policy -> label GUI acceptance unverified and direct local execution to the capable Code host; do not silently rewrite upstream packages.
- New guide distracts from existing GUI-first onboarding -> link prerequisites clearly while preserving companion installation entry points.
- Parallel work edits the same prose -> compare the live target documentation before any authorized integration; do not edit the sibling change or infer compatibility from a clean merge.
- A documentation command overwrites skills or changes the wrong profile -> explicit selection, preflight/review, backup advice and no blanket overwrite/force examples.

## Migration Plan

No runtime/data migration or deployment is needed. After approval, implement only the documentation delta in this worktree and complete the local gates/review. Any source publication, merge, archive/receipt and issue closure follows separately authorized finish. Recovery is correction or reversal of the documentation delta; real installs are outside this change.
